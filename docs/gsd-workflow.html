2 核心命令详解
命令

/gsd-new-project

初始化全新项目。深度上下文采集 → PROJECT.md → 需求 → 路线图。支持从现有文档自动初始化。
1 提问环节 — 项目是什么、技术栈偏好、约束
2 并行研究 — 4 路 project-researcher (Stack/Features/Arch/Pitfalls)
3 需求定义 — 分类 scoping，生成 REQUIREMENTS.md + REQ-ID
4 路线图创建 — roadmapper 生成 ROADMAP.md + STATE.md
.planning/PROJECT.md .planning/ROADMAP.md .planning/STATE.md .planning/REQUIREMENTS.md .planning/research/
重要参数： --auto @prd.md 从已有 PRD/想法文档自动初始化，跳过交互提问。
命令

/gsd-new-milestone

启动新里程碑。加载旧 PROJECT.md → 采集目标 → 更新 → 需求 → 路线图。
1 采集里程碑目标 — MILESTONE-CONTEXT 或对话
2 确定版本号 + 验证理解
3 更新 PROJECT.md + 重置 STATE.md
4 可选研究 (4 researcher → synthesizer)
5 需求定义 + 路线图创建 (roadmapper)
PROJECT.md (更新) STATE.md (重置) ROADMAP.md (追加) REQUIREMENTS.md (新里程碑)
命令 子 Agent × 2

/gsd-discuss-phase

收集阶段实现决策。分析灰区 → 用户选择 → 深度讨论 → 记录决策。支持链式自动化。
1 加载先验上下文 (PROJECT/REQUIREMENTS/STATE + 前 3 个 CONTEXT)
2 代码库侦察 — 复用资产、现有模式、集成点
3 识别灰区 — 标注已有决策，跳过已决定问题
4 用户选择讨论区 → 逐区深度讨论 (每区 4 问)
5 写 CONTEXT.md + DISCUSSION-LOG.md
{phase}-CONTEXT.md {phase}-DISCUSSION-LOG.md
重要参数： --chain 自动链式推进不暂停；--power 从文件批量输入；--assumptions 预览 AI 预期方法（仅预览不写文件）。
命令 子 Agent × 3

/gsd-plan-phase

创建可执行计划。可选研究 → 规划 → 验证 → 修订循环 (最多 3 轮)。
1 加载 CONTEXT.md — 用户决策锁
2 可选研究 — gsd-phase-researcher 生成 RESEARCH.md
用 --research-phase 仅做深度生态研究
3 可选 UI-SPEC — gsd-ui-phase 生成设计契约
4 生成计划 — gsd-planner 写 PLAN.md 文件
5 验证计划 — gsd-plan-checker → 修订循环 (≤3 轮)
6 需求覆盖门 + 决策覆盖门 → 提交
{phase}-PLAN.md (×N) {phase}-RESEARCH.md {phase}-PATTERNS.md STATE.md (更新)
命令 子 Agent × N

/gsd-execute-phase

波次并行执行。发现计划 → 按波分组 → 并行 spawn → 合并 → 验证。
1 发现计划 — plan-index 按波分组
2 每波: 文件冲突检测 → 串行化重叠计划
3 spawn gsd-executor (worktree 隔离) × 波内计划数
4 合并 worktree → post-merge 测试门
5 更新 ROADMAP/STATE 追踪
6 全波完成 → 代码审查门 → 回归门 → 验证阶段目标
{phase}-SUMMARY.md (×N) {phase}-VERIFICATION.md ROADMAP.md (更新) STATE.md (更新)
命令 门

/gsd-verify-work

对话式用户验收测试。基于 VERIFICATION.md 的 human_verification 项逐项确认。

6 execute-phase 并行隔离机制
机制

Wave 波次模型

计划按依赖关系分组为波次。波 1 先执行，完成后波 2 才能在波 1 产物基础上构建。
1 PLAN.md frontmatter 声明 wave 编号
2 编排器按 wave 分组，逐波执行
3 波内并行 (无文件冲突时)，波间串行
4 每波结束: 合并 worktree → 测试门 → 下一波
机制

Git Worktree 隔离

每个 executor Agent 在独立 git worktree 中运行。避免并行计划之间的文件冲突。
1 Agent(isolation="worktree") 创建临时分支
2 executor 在隔离目录中提交
3 波结束: merge --no-ff 回到主分支
4 文件冲突检测: 重叠则串行化该波
机制

Worktree 路径安全

executor 不得修改 STATE.md/ROADMAP.md。编排器在所有 worktree 合并后统一更新。
1 executor 提交 SUMMARY.md 到工作树
2 合并时 STATE.md/ROADMAP.md 主分支版本优先
3 编排器单点更新追踪文件
4 前删除检查 + 批量删除审计门
7 日常开发场景命令
命令 轻量

/gsd-quick

快速执行小任务。跳过可选 Agent（research/pattern-map），直接规划 + 执行 + 提交。适合文档更新、小修复、单文件改动。
1 用户描述任务 → 自动生成轻量 PLAN.md
2 直接执行 (单 executor，无 worktree 隔离)
3 原子提交 + 状态更新
PLAN.md (轻量) SUMMARY.md Git Commit
适用场景： 修 typo、更新文档、小重构、加注释、调配置。不适合多文件架构变更。
命令 子 Agent × N

/gsd-debug

系统化调试流程。科学方法驱动：复现 → 缩小 → 假设 → 打点 → 修复 → 回归。支持跨会话检查点恢复。
1 问题描述 → gsd-debug-session-manager 创建调试会话
2 spawn gsd-debugger — 复现 bug，收集日志/堆栈
3 最小化复现用例 → 形成假设 → 打点验证
4 定位根因 → 生成修复 → 回归测试
5 检查点保存 (AskUserQuestion) → 支持中断后继续
6 修复提交 + DEBUG-REPORT.md 记录
DEBUG-REPORT.md CHECKPOINT.md (可恢复) Git Commit (修复)
适用场景： 测试失败、运行时异常、性能回归、逻辑 bug。不适合：功能开发、新需求。
重要参数： --diagnose 仅诊断不修复，先了解问题再决定方案。
命令 子 Agent 质量门

/gsd-code-review

对阶段变更文件进行代码审查。检查 bug、安全问题、代码质量。可选 --fix 自动修复。
1 加载阶段 PLAN.md → 提取变更文件列表
2 spawn gsd-code-reviewer — 多维度审查
3 生成 REVIEW.md — 按严重度分级 (HIGH/MEDIUM/LOW)
4 可选 --fix: spawn gsd-code-fixer 逐项修复
{phase}-REVIEW.md Git Commit (修复, 可选)
适用场景： 阶段完成后、PR 提交前、重大重构后。execute-phase 自动在波次完成后调用。
命令 自主管道

/gsd-audit-fix

自主审计到修复管道。发现 → 分类 → 修复 → 测试 → 提交，全自动闭环。
1 自动扫描代码库 → 发现潜在问题
2 按类型/严重度分类 → 生成修复计划
3 逐项修复 → 运行测试 → 原子提交
AUDIT-REPORT.md Git Commits (×N)
适用场景： 技术债务清理、代码质量提升、批量小修复。适合 "帮我整体检查一下代码质量"。

命令 审计 Agent

/gsd-secure-phase

回顾性验证阶段的威胁缓解措施。对照 PLAN.md 威胁模型检查代码实现。
1 加载 PLAN.md → 提取威胁模型条目
2 spawn gsd-security-auditor → 逐项检查代码

2 spawn gsd-ui-auditor → 6 维度评分

{phase}-UI-REVIEW.md

命令 评估审计

/gsd-eval-review

审计 AI 集成阶段的评估覆盖。对照 AI-SPEC.md 评估计划检查实现。

2 spawn gsd-eval-auditor → 逐维度评分
3 生成 EVAL-REVIEW.md — COVERED/PARTIAL/MISSING

2 spawn gsd-nyquist-auditor → 检查测试覆盖
3 生成 VALIDATION.md + 自动补全缺失测试
{phase}-VALIDATION.md test_*.py (新增测试)
适用场景： 阶段完成后验证测试覆盖。适合 "这个阶段测够了吗？" 的疑问。
9 探索与创意
命令 HTML 原型

/gsd-sketch

用即抛型 HTML 模拟稿快速可视化 UI 想法。无需搭建完整前端环境，直接生成可交互的静态页面。
1 描述 UI 想法 → 生成独立 HTML 文件
2 内联 CSS + 模拟数据 → 浏览器直接打开
3 迭代修改 → 满意后转为正式 UI-SPEC
sketches/*.html
适用场景： "这个界面长什么样？"、"帮我快速画一个 dashboard 布局"、UI 方案对比。
命令 实验代码

/gsd-spike

通过体验式探索验证技术想法。写实验代码来回答 "这个方案可行吗？" 而非直接进入正式开发。
1 描述技术问题 → 生成探索计划
2 写最小实验代码 → 运行验证
3 记录结论 → 决定是否纳入正式计划
spikes/*.md spikes/*.py (实验代码)
适用场景： "用 asyncio.Queue 还是 Redis pub/sub？"、"这个库的 API 好用吗？"、技术选型验证。
命令 创意路由

/gsd-explore

苏格拉底式构思与创意路由。在提交计划前，通过对话深挖想法、识别盲区、评估可行性。
1 用户提出模糊想法 → AI 提问深挖
2 识别相关决策、交叉影响、潜在风险
3 路由建议: 进入 sketch / spike / discuss-phase / 放弃
EXPLORATION.md (可选)
适用场景： "我有一个想法但不确定是否靠谱"、"这个功能值得做吗？"、早期头脑风暴。
命令 收件箱

/gsd-capture

快速捕获想法、任务、笔记和种子，路由到正确的目标位置。不丢失任何灵感。
1 用户口述想法 → AI 分类 (idea/task/note/seed)
2 路由到对应目标: backlog / ROADMAP / 笔记 / spike
3 生成追踪引用 → 后续可检索
INBOX.md (追加) BACKLOG.md (可选)
适用场景： "记一下，回头可能需要..."、"有个想法先存着"、开发中冒出的灵感。

命令 诊断

诊断 .planning/ 目录健康状态。检测不一致、缺失文件、损坏引用，可选自动修复。

HEALTH-REPORT.md

2 智能路由: 继续当前阶段 / 跳到下一步 / 处理阻塞

(路由到对应命令)

11 高级编排与协作
命令 自主模式

/gsd-autonomous

自主运行所有剩余阶段。discuss → plan → execute → verify 全自动循环，直到里程碑完成或遇到阻塞。
1 读取 ROADMAP.md → 确定未完成阶段列表
2 逐阶段自动 discuss → plan → execute → verify
3 遇到需用户决策时暂停 (AskUserQuestion)
4 全部完成或阻塞时报告
所有阶段产物 (自动生成)

命令 并行流

/gsd-workstreams

管理并行工作流。创建、切换、查看多个独立工作流 — 每个有独立 STATE 和上下文。

4 complete: 合并工作流结果回主线
.planning/workstreams/*.md
适用场景： 多人协作 (每人一个 workstream)、同时推进多个独立阶段、实验性分支开发。
命令 持久上下文

/gsd-thread

管理跨会话持久上下文线程。保持长期运行的讨论或任务在多次对话中连续。
1 create: 创建命名线程 → 保存当前上下文
2 resume: 恢复线程 → 加载完整对话历史摘要
3 list/delete: 管理活跃线程
.planning/threads/*.md
适用场景： 跨越多天的架构讨论、等待外部反馈的决策、需要反复回顾的复杂设计话题。

2 发送到外部 AI (不同模型/提供商)
3 收集审查意见 → 汇总 REVIEW-FEEDBACK.md
{phase}-REVIEW-FEEDBACK.md

16 故障排除速查
问题方案
"项目已初始化"删除 .planning/ 目录重新开始
长会话上下文退化用 /clear 清除上下文，再用 /gsd-resume-work 恢复
计划方向错误先运行 /gsd-discuss-phase [N] 锁定决策，或用 --assumptions 预览
执行失败 / 计划过大计划最多 2-3 个任务，缩小范围重新规划
忘记当前进度运行 /gsd-progress 查看状态和下一步
执行后需要小修改用 /gsd-quick 针对性修复，无需重新执行整个阶段
STATE.md 不同步state validate → state sync --verify → state sync
模型成本太高/gsd-config --profile budget，禁用非必要 Agent
敏感项目设置 commit_docs: false，将 .planning/ 加入 .gitignore
更新覆盖本地修改/gsd-update --reapply 恢复本地修改
子 Agent 报告失败但代码已写好检查 git log — 工作可能已成功提交
